### Security Considerations

[Source: architecture/8-security-architecture.md]

- PII encryption at rest (DB/objects) + in transit
- NRIC stored as salted hash
- Rate limiting via Redis (token bucket) for hot endpoints
- Audit logs for login, rate, bind, JPJ submit, claims (immutable)
- Row Level Security (RLS): Customer reads gated by `user_id = current_user_id()`

### Risk Assessment & Design Review (Draft Stage)

#### 🔴 High-Risk Areas Identified

1. **Database Schema Complexity**

   - **Risk**: Creating 11+ tables with complex relationships in initial setup
   - **Impact**: High - Schema changes later will require migrations
   - **Mitigation**: Consider phased approach - start with core tables (users, quotes, policies) and add others incrementally
   - **Design Recommendation**: Implement schema versioning from day one

2. **Multi-Environment Secrets Management**

   - **Risk**: Managing PSP keys, JPJ certificates, NCD keys across dev/staging/prod
   - **Impact**: Critical - Potential security breach if mishandled
   - **Mitigation**: Implement secrets rotation strategy and audit logging from start
   - **Design Recommendation**: Use HashiCorp Vault or AWS Secrets Manager with strict IAM policies

3. **Dual Deployment Target (Fly.io OR AWS)**
   - **Risk**: Ambiguity in deployment target could lead to incompatible configurations
   - **Impact**: High - Rework required if wrong choice made
   - **Mitigation**: Make deployment decision before implementation begins
   - **Design Recommendation**: Start with one platform, document migration path to other

#### 🟡 Medium-Risk Areas

1. **Redis Configuration Missing**

   - **Risk**: Rate limiting and caching mentioned but Redis setup not in tasks
   - **Impact**: Medium - Performance issues without proper caching
   - **Mitigation**: Add explicit Redis setup task with connection pooling
   - **Design Recommendation**: Use Redis Sentinel for HA from the start

2. **OpenAPI Specification**

   - **Risk**: openapi.yaml referenced but no task to create it
   - **Impact**: Medium - Contract testing will fail without spec
   - **Mitigation**: Add OpenAPI generation from NestJS decorators
   - **Design Recommendation**: Use @nestjs/swagger for auto-generation

3. **Magic Link Flow Complexity**
   - **Risk**: Passwordless auth requires email service integration from day one
   - **Impact**: Medium - Can't test auth flow without email service
   - **Mitigation**: Implement fallback dev mode with console output
   - **Design Recommendation**: Abstract email provider with adapter pattern

#### 🟢 Design Strengths

1. **Modular Architecture**: NestJS modules align well with bounded contexts
2. **Security First**: PII encryption, NRIC hashing, audit logs planned from start
3. **Testing Strategy**: Comprehensive test types identified early
4. **Infrastructure as Code**: Terraform mentioned for repeatability

#### 🏗️ Architectural Recommendations

1. **Repository Structure**

   ```
   auto-insurance/
   ├── packages/
   │   ├── backend/         # NestJS monolith
   │   ├── frontend/        # Next.js app
   │   ├── shared/          # Shared types/utils
   │   └── infrastructure/  # Terraform/IaC
   ├── .github/
   │   └── workflows/       # CI/CD pipelines
   └── docker-compose.yml   # Local dev environment
   ```

2. **Database Migration Strategy**

   - Use Prisma's shadow database for migration testing
   - Implement backward-compatible migrations only
   - Add migration rollback scripts from start

3. **Feature Flag Implementation**

   - Consider LaunchDarkly or Unleash for dynamic flags
   - Implement kill switches for critical features
   - Add feature flag audit logging

4. **Monitoring & Observability**
   - OpenTelemetry mentioned but not configured
   - Add Grafana/Prometheus setup task
   - Implement structured logging from day one

#### 🔒 Security Design Considerations

1. **JWT Token Strategy**

   - Short-lived access tokens (15 min)
   - Refresh tokens with rotation (7 days)
   - Implement token blacklisting for logout

2. **Rate Limiting Design**

   - Token bucket per user ID
   - Global rate limits for anonymous endpoints
   - Implement progressive delays for failed auth

3. **Audit Log Design**
   - Immutable append-only table
   - Separate audit database consideration
   - Include request IDs for traceability

#### ⚠️ Compliance & Regulatory Risks

1. **Malaysian Regulatory Requirements**

   - JPJ integration requires official certification process
   - SST calculation must be auditable
   - Personal data must comply with PDPA

2. **Data Residency**
   - Ensure Singapore/Malaysia deployment for data sovereignty
   - Document cross-border data transfer policies

#### 📋 Task Sequencing Risks

1. **Parallel Task Dependencies**
   - Database must exist before auth module
   - CI/CD needs repos to exist first
   - Consider DAG for task dependencies

#### 🚀 Performance Considerations

1. **Database Indexing Strategy**

   - Indexes listed but performance impact not assessed
   - Add EXPLAIN ANALYZE requirements to tests
   - Consider partial indexes for large tables

2. **Caching Strategy**
   - No explicit cache invalidation strategy
   - Add cache warming for critical data
   - Implement cache-aside pattern properly
